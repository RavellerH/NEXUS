D01

Deployment Model: Self-Hosted Docker Compose

Locked All Phases

NEXUS is a self-hosted product. Clients deploy and run it on their own VPS using Docker Compose. The builder does not manage client infrastructure.

Rationale: SaaS means owning client uptime. One crash or bad deployment stops product development while the builder firefights. Self-hosted shifts infra responsibility to the client. The blame changes form but loses urgency and removes on-call burden.
Constraints: docker-compose up must work first time, every time. JWT secret generated per-installation. License enforcement must work without a persistent central server.
D02

Business Model: Annual License Key

Pending builder confirmation Phase 4

NEXUS is sold as an annual renewable license. Client pays → receives license key valid for 12 months. Non-renewing clients keep the product working on their current version.

Rationale: One-time pricing creates a revenue cliff. Monthly SaaS has ongoing service connotations the builder doesn't want. Annual license is standard in B2B, expected by company procurement departments, and creates a renewal cohort.
Tiers (future): Solo PM (1 install, 3 projects) · Team (unlimited projects) · Agency (5 installs)
D03

LLM: Qwen2.5-7B via Ollama

Locked Phase 1

Use qwen2.5:7b via Ollama instead of Hermes3. ~5 GB Q4_K_M quantized.

Rationale: Hermes3 is English-first. SEA EPC teams code-switch between Bahasa Indonesia and English in WhatsApp and documents. Qwen2.5-7B has significantly better multilingual SEA performance with similar VRAM requirements. Both run via Ollama with no architecture change.
D04

Embedding Model: multilingual-e5-large (1024d)

Locked Phase 1

Use intfloat/multilingual-e5-large for embeddings. 1024 dimensions. Must be set consistently from day 1 — ChromaDB collections are dimension-locked.

Rationale: nomic-embed-text degrades on Bahasa Indonesia. WhatsApp chats — the most critical knowledge source — are in Bahasa or mixed language. Poor embedding = poor retrieval regardless of model quality.
Critical: Changing embedding model after ingestion requires full re-ingestion. Document clearly in setup guide.
D05

Multi-tenancy: One ChromaDB Collection Per Project

Locked Phase 1

Each project gets its own named ChromaDB collection: nexus_project_{project_id}. All queries scoped to the active project_id. No cross-project retrieval.

Rationale: Simplest isolation model. No risk of cross-project bleed. No complex filter logic in every query. Alternatives (filtering by metadata within a shared collection) add complexity without benefit at this scale.
D06

JWT Auth: project_id + role Claims

Locked Phase 1

Every JWT carries two custom claims: project_id (string) and role (enum: pm | engineer | field_tech | procurement).

Rationale: project_id required for D05 collection scoping. role required for Phase 3 intent-aware retrieval but must be in token schema from day 1 to avoid a token migration later. Default Phase 1: pm for admin, engineer for others.
D07

Authority Hierarchy: Configurable Per Project

Locked Phase 2

Authority levels are not globally hardcoded. PM admin configures hierarchy per project. Default 5-level hierarchy provided if not configured.

Rationale: Real EPC organizations differ. In safety-critical contexts, a field tech's on-site WhatsApp hazard report may override a SOP. The hierarchy must be editable per project, not globally fixed.
D08

Project Switcher: Phase 1 (moved from Phase 3)

Locked Phase 1

The project switcher UI component is a Phase 1 requirement. A PM managing many concurrent projects needs to switch project context from day 1.

Rationale: A PM running 8 concurrent projects with no switcher will not use the product. The ChromaDB collection-per-project design (D05) makes this straightforward: switching projects just changes the active project_id in the session.
D09

P&ID Tag Extraction: Phase 1 (moved from Phase 4)

Locked Phase 1

Basic P&ID instrument tag extraction (regex-based) in Phase 1. Advanced OCR-based parsing remains Phase 4.

Rationale: "What is the spec for AT-201?" is one of the most common EPC queries. The MVP without tag extraction cannot answer it. Regex patterns ([A-Z]{2,4}-\d{3,4}) cover 80% of cases and can be implemented in hours.
D10

Reference Deployment: DigitalOcean Singapore 16GB

Locked Phase 1

Official documented deployment spec: DigitalOcean Singapore, 16 GB RAM, 8 vCPU Droplet. ~$96 USD/month.

Rationale: Low latency for SEA clients. PM-friendly dashboard. 16 GB fits Qwen2.5-7B Q4_K_M (~5 GB) + ChromaDB + FastAPI + React with headroom. Within budget for a business-critical tool.
D11

Chunking: Document-Type-Specific Per Parser

Locked Phase 1

Each parser implements its own chunking strategy. No shared naive chunker.

Rationale: Naive fixed-size chunking breaks table rows mid-row, splits SOP steps mid-instruction, severs BOM line items from column headers. Poor chunking directly causes poor retrieval regardless of embedding quality.
Strategy by type: WhatsApp → by message, grouped by date window · PDF → by paragraph, section headers respected · P&ID → per instrument tag region · Excel BOM → by row, column headers prepended · DOCX SOP → by section heading, numbered steps preserved · Email → by message, reply context preserved
D12

WhatsApp Language: Multilingual Code-Switching (Bahasa + English)

Locked Phase 1

Target clients' WhatsApp project chats are multilingual with heavy code-switching between Bahasa Indonesia/Malay and English.

Rationale: Confirms D04 (multilingual-e5-large) and D03 (Qwen2.5-7B). WhatsApp parser will support multilingual content from day 1, avoiding subsequent parsing or embedding dimension migrations.
D13

Distribution Format: Zip File / Private GitHub Repo

Locked Phase 1 Phase 4

Phase 1: private GitHub repo + downloadable ZIP with docker-compose.yml. Phase 4: private Docker Hub with license checks.

Rationale: Minimizes launch overhead for early clients. Allows trust-based adoption initially. Technical IP protection and programmatic validation deferred to Phase 4 commercialization.
D14

License Pricing: Recurring Annual / Monthly Renewal

Locked Phase 4

Recurring subscription-like license key (annual or monthly options) over a flat one-time purchase.

Rationale: Mitigates revenue cliff risk. Supports ongoing maintenance. Aligns with B2B software purchasing cycles expected by company procurement in Southeast Asia. Active subscriptions authorize clients to pull future updates and access support.
